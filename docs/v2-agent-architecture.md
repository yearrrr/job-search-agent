# 第二版整体架构与调用方式

截至 2026-09-15，前三批已实现：资料解析、JD 解析、岗位准备分析、项目推荐、人工选择、完整简历撰写、版本确认和 Word/PDF 导出。第四批为真实场景联调验收，模拟面试 Agent 尚未实现。

## Agent 与模型任务

当前只有 **1 个具有自主检索循环的主求职 Agent**，用于岗位准备分析。资料解析、JD 解析、项目推荐与简历写作是四类有明确输入输出的 LLM 任务，不是四个独立自治 Agent。

| 组件 | 如何运行 | 代码入口 |
| --- | --- | --- |
| 主求职 Agent | LangGraph 的模型节点与工具节点循环；模型决定检索内容、读取详情与核对依据，最后返回匹配结果和准备建议 | agent/preparation.py |
| 简历/项目解析 | 读取页面图片或文本，LLM 整理完整经历与来源，等待人工核对 | services/profile_parser.py |
| JD 解析 | LLM 整理文字/截图中的岗位字段，人工核对后入库 | services/jd_v2.py |
| 项目推荐 | 将当前资料区已确认项目及 JD 要求交给模型排序，返回项目编号、推荐理由、对应要求；本分支无需重复调用检索工具 | services/resumes_v2.py |
| 简历撰写 | 只发送人工选定的非基础经历和 JD；逐段返回正文与对应经历编号，基础信息在本机回填 | services/resumes_v2.py |

这些任务共用 DeepSeek 模型适配层和预算设置。模型任务数、API 调用次数、Agent 数量是不同概念。

## 整体流程

~~~mermaid
flowchart TD
  A[简历或项目原件] --> B[LLM 资料解析]
  B --> C[人工分类核对与确认]
  C --> D[(SQLite 已确认经历库)]
  E[JD 图片或文本] --> F[LLM 岗位解析]
  F --> G[人工核对岗位]
  G --> H{是否需要准备分析}
  H -->|需要| I[主 Agent 检索工具循环]
  D --> I
  I --> J[匹配依据 待确认问题 学习建议]
  J --> K[项目选择工作台]
  H -->|直接准备简历| K
  D --> L[LLM 项目推荐]
  G --> L
  L --> K
  K --> M[人工选用 排除 排序 写作偏好]
  M --> N[LLM 撰写完整简历]
  N --> O[来源编号与数字校验]
  O --> P[逐段编辑 保存草稿 人工确认]
  P --> Q[(不可变简历版本)]
  Q --> R[Word 与 PDF 本地导出]
~~~

## 主 Agent 的工具

工具定义位于 agent/experience_tools.py，仅用于读取当前任务快照允许的资料。

| 工具 | 参数 | 返回内容 |
| --- | --- | --- |
| search_experiences | query、categories、limit | 最多 12 条已确认经历摘要及编号 |
| get_experience_details | experience_ids | 最多 8 条已发现经历的完整内容 |
| get_evidence | fact_ids | 最多 8 条已读取经历的来源摘录、页码/行号 |

例如模型需要核对 RAG 项目，会先返回 search_experiences 工具请求。执行器验证参数、预算、资料版本，再调用对应函数，把查询结果作为工具消息交给模型。模型随后可请求详情与证据，最后给出分析。无效编号整批拒绝，并返回合法编号提示；最多反馈 3 次纠正机会，不进行模糊匹配。重复查询优先复用同任务缓存。

模型无法提交 SQL、任意文件路径或其他资料区参数。岗位状态修改、资料确认、材料保存和导出均由用户操作触发，未开放为模型写入工具。

## 第三批为什么保留经历编号

推荐阶段只能引用当前候选项目的编号。生成阶段把人工选定的编号和顺序固定在任务快照中；每段正文必须对应其中一个编号，不能漏项、插入未选经历或改变顺序。

数字校验要求每段的数字来自它自己的经历，避免把另一项目的指标或 JD 中的要求搬过来。学校、单位、角色、时间沿用已确认档案元数据，用户可以在原档案修改后重新生成。无法用程序完全判定所有语义改写是否准确，因此页面仍要求逐段核对和明确确认。

推荐和写作采用固定流程，输出结构不合规时最多重写 2 次，均计入原任务调用预算；不确定超时不自动重发。相同资料、岗位、所选经历、顺序、偏好和运行方式复用已完成结果。更改这些输入后才创建新的生成任务。

## 数据、恢复与隐私

- SQLite 保存已确认经历、原件位置、岗位、模型和工具尝试、草稿历史与已确认版本。第三批迁移到 schema 7，只新增三张简历表。
- 任务快照保存使用的岗位、事实修订、结构化元数据与选择顺序。资料变化后不能把旧草稿确认为新版本；历史已确认文件仍按原内容下载。
- 草稿采用乐观版本校验；确认在事务内分配版本号，重复点击返回同一版本。
- V2 中断恢复按持久化调用账本重放确定结果；已有调用和预算不清零。未知调用结果保持停止，避免重复费用。首版仍保留 LangGraph SQLite 检查点机制。
- 第三批只发送推荐所需的已确认项目，或写作所需的已选非基础经历；手机号与邮箱在发送前隐藏，基础信息在本机回填。此前视觉解析仍会发送用户上传的原件图像，应以各入口提示为准。
- Word/PDF 从同一已确认内容生成，无额外模型调用；默认使用 11pt 中文字体自动分页，两种格式分页不保证完全一致。

新任务限额：单次输出 102,400 Token、文本请求 100,000 字符、模型调用 40 次、工具调用 60 次。上限不是必须用满的目标；长输入超出限制会停止并保留记录。

第三批工程测试与真实模型样例见[交付记录](v2-batch-three-report.md)。样例通过不等于用户真实简历已经完成效果验收。
