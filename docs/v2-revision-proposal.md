# 第二版个人求职助手：修改方案（讨论稿）

状态：用户已授权开发。前三批均已交付，见[第一批记录](v2-batch-one-report.md)、[第二批记录](v2-batch-two-report.md)、[第三批记录](v2-batch-three-report.md)。本批先由用户体验项目推荐和定制简历，第四批再进行真实场景联调。模拟面试仍是后续扩展。

用户已确认两个选项：

- 完整简历默认导出 Word＋PDF。
- 输入长度、任务模型调用次数、工具调用次数放宽至当前的五倍，并优化重复检索。
- 用户随后将单次输出上限进一步调整为 102,400 Token，替代此前的 10,240 Token 方案。

## 1. 第二版目标

由 LLM 理解简历和岗位截图，建立可持续维护的个人经历库；用户确认后，Agent 根据岗位分析差距、推荐项目，并撰写适合该岗位的完整简历。操作应当连续，确认和编辑不整页刷新。

第二版主要处理本次反馈的第 1–8 项。第 9 项模拟面试官及面经搜索在主流程完成并验收后单独讨论。

## 2. 问题与修改对应

| 用户反馈 | 修改方案 | 验收方式 |
| --- | --- | --- |
| 1. 简历按脚本规则解析不准确 | LLM 负责识别语义、合并跨行内容、归类和提取结构。PDF 页面或截图由视觉模型读取；纯文本直接交给文本模型。程序只负责读取/转换文件、校验和存储，不再按小标题规则生成正式解析结果 | 使用多栏、跨页、换行混乱的简历核对项目归属、时间、技术与成果，无证据的信息标为待核对 |
| 2. 分类不符合实际使用 | 六个主分类：项目、实习经历、掌握技能、学历、获得奖项、专利/论文；另有基础个人信息。按完整经历分组，不把每一行都当成独立项目 | 一个项目的名称、时间、角色、技术、职责和成果在同一卡片中，来源可回查，历史分类可迁移 |
| 3. 确认操作刷新页面 | 确认、修改、排除及批量确认通过局部请求完成，保留滚动位置和其他未保存编辑。成功后更新该卡片与待确认数量，失败在原处说明 | 连续操作多张卡片无整页跳转；重复点击不重复写入；过期编辑给出局部冲突提示 |
| 4. 缺少下一步入口 | 增加步骤指引、已确认数量、“保存并继续 → 导入岗位”。允许将部分内容留待核对，后续仅使用已确认信息 | 从上传简历到导入 JD 每一步都有明确入口，退出后可回到原进度 |
| 5. 希望由图片解析 JD | 支持上传/粘贴单张或多张岗位截图，以及直接粘贴文本。LLM 提取公司、岗位、来源链接、批次、JD 原文、职责、硬性要求、加分项等；进入可编辑核对页后保存 | 截图中有的信息准确保留；没有展示的链接、批次等留空待补充；不自动编造外部链接 |
| 6. 切换准备中时询问是否分析 | 状态切换成功后展示一次选择：“分析匹配情况并生成准备清单”或“暂时只更新状态”。选择分析才启动任务，结果显示证据、缺口、建议学习内容和优先级，并提供生成简历入口 | 未选择分析时没有模型调用；重复提交或刷新不重复启动；可稍后从岗位页启动 |
| 7. 限制过紧 | 单次输出上限调整为 102,400 Token；文本输入、模型次数与工具次数按五倍调整，同时去除无效重复检索并显示已有用量 | 正常简历/JD 能完成闭环；达到上限时可解释，已有结果保留；不能通过恢复重置预算 |
| 8. 希望维护更多项目并按岗位生成简历 | 扩展现有 SQLite 为个人经历库，支持独立新增项目/经历，不要求先修改原简历。LLM 根据岗位选择项目并说明理由，用户可锁定、排除、换序，再由 LLM 撰写完整简历 | 同一档案针对两种不同 JD 能给出可解释的选项；允许用户改选；Word/PDF 与确认内容一致 |
| 9. 模拟面试官 | 后续版本再做，届时讨论基于简历、项目、JD 和小红书/牛客面经的模拟问答、追问和反馈 | 本轮不作为开发或验收项 |

## 3. 新的使用流程

上传简历或补充项目
→ LLM 解析与分组
→ 原地编辑、确认个人经历
→ 点击“下一步：导入岗位”
→ 上传 JD 图片或粘贴文本
→ LLM 提取并由用户核对岗位信息
→ 将岗位设为“准备中”
→ 用户选择是否进行岗位准备分析
→ 查看匹配依据、需要确认的信息、学习建议
→ 查看推荐项目并调整
→ LLM 撰写完整简历
→ 编辑、确认、保存版本
→ 导出 Word＋PDF。

学习建议与个人经历分开存放。缺少证据不能直接等于用户不会某项技能；完成学习待办也不自动成为已确认履历。

## 4. 关键设计

### 4.1 LLM 解析与来源

文件转换不承担语义判断：例如 PDF 转为页面图片后由视觉模型阅读，文本输入保持段落结构。模型合并跨行项目、识别所属模块，输出有来源的结构化记录。

保留原文件及解析版本。每条经历保存来源页/原文片段，模糊、遮挡或缺失的字段标记待核对。重新解析产生待核对版本，不覆盖已确认事实。模型输出允许合理整理语言，但不得自行补齐未出现的学历、任职单位、时间和成果。

图片解析优先沿用当前 DeepSeek 服务。重新核对官方现行视觉文档后，deepseek-flash 已支持图片；旧的 deepseek-v4-flash-vision-exp 名称请求由最新 Flash 承接。本方案更新为优先使用现有 Flash 的图片输入能力，扩展当前只发送文本的适配层。实施时先用非敏感合成样例验证账号、型号和接口兼容，再用实际资料验收识别效果。

参考：[DeepSeek 视觉输入官方说明](https://api-docs.deepseek.com/guides/vision/)。

### 4.2 个人经历库

复用已有 SQLite、原件和确认历史，通过版本化迁移补齐实体和关系：

- 基础信息：姓名、联系方式、求职目标等。
- 经历条目：项目、实习、技能、教育、奖项、专利/论文。
- 项目/实习结构：名称、时间、角色、技术标签、工作内容、成果、确认状态。
- 来源记录：上传原件、来源位置或用户主动补充的说明，以及修订历史。
- 岗位与分析：岗位版本、需求、采用的经历版本、分析和准备计划。
- 简历版本：目标岗位、选用项目、生成稿、人工编辑稿及导出文件。

新增项目可以直接填写或上传说明，仍需用户确认。历史资料保留；旧“实践经历/其他”等分类无法明确转换时列为待核对，不自动丢弃。笔记和生成稿不进入事实检索结果。

### 4.3 按岗位生成完整简历

模型先阅读岗位要求，再检索已确认经历，输出推荐项目、排序、采用理由及未覆盖要求。用户能够锁定或排除项目。

撰写阶段由 LLM 组织措辞、重点与段落，覆盖完整简历需要的基本信息、教育、技能、经历和其他相关模块；不再只拼接原句。完整简历与事实依据之间保留映射，来源说明在核对页展示，正式导出保留求职内容。

日期、公司、学历、数字成果等关键事实核对来源；模型可以改写表达，不能发明经历或把学习计划写成实际经验。不采用“再用一个模型审核就保证真实”的验收方式，以用户对照来源确认结果为准。

Word 用于后续编辑，PDF 用于投递；两者从同一已确认简历版本导出，检查字体、分页、截断与可复制文字。视觉格式属于该阶段的实际交付，不止生成文件扩展名。

### 4.4 页面交互

保留当前 Web 技术路线，增加局部更新和明确的步骤导航。确认请求成功后再改变状态；网络失败保留输入并允许重新提交。多人不在当前场景内，但多标签页的旧修订冲突仍需处理。

批量确认必须是用户主动选择的操作。个人资料页、JD 核对页、岗位分析页、简历预览页均提供下一步入口。任务处理中展示当前动作、已获得的结果和调用消耗；详情显示工具输入摘要、结果与依据，不展示模型隐藏推理。

### 4.5 Agent 与程序分工

继续以一个主 Agent 和明确工作流组织业务，不把解析、查询、保存等普通模块都包装成独立 Agent。

LLM 负责理解、归类、匹配、决定如何查找经历、提出补充问题、推荐项目和撰写简历。

程序负责执行工具、存储、来源与版本校验、局部页面更新、状态变更、人工确认、预算和恢复。

针对重复检索，记录查询范围和已有结果，在同一档案版本内复用完全相同的查询；补充事实或岗位版本变化后重新检索。压缩已重复出现的工具历史，避免无限扩大提示词。是否需要更多证据应能从已有覆盖情况判断。

## 5. 已确认的新限额

以下限额已应用于配置默认值及本机 .env，新任务使用新限额，旧任务保留原预算。

| 项目 | 当前值 | 第二版目标 |
| --- | --- | --- |
| 单次输出上限 | 2,048 Token | 102,400 Token |
| 单次文本输入长度 | 20,000 字符 | 100,000 字符 |
| 每任务模型调用上限 | 8 次 | 40 次 |
| 每任务工具调用上限 | 12 次 | 60 次 |

字符数和 Token 分开计量；图片单独按张数、尺寸和请求体大小限制，不将 Base64 字符串当成自然语言的 Token 长度。上限是允许的最大值，不要求每次用满；记录实际输入/输出用量。

上次达到 budget 的任务原因是调用次数限制，不能仅扩大输出 Token。第二版同时修复重复检索问题；有限重试和不确定请求停止重发的规则继续保留。修改配置默认作用于新任务，旧任务保留原预算和历史记录。

## 6. 开发顺序与逐批验收

| 批次 | 交付内容 | 用户验收重点 |
| --- | --- | --- |
| 开始前 | 备份当前版本与全部数据，记录现有失败案例；验证模型能力与迁移方案 | 可恢复到旧版；原件、已确认事实和材料完整 |
| 第一批：资料入口 | 视觉/文本 LLM 解析、六类个人经历库、独立新增项目、无整页刷新确认、下一步导航；接入新限额与用量记录 | 简历解析准确度、项目是否完整归组、连续确认是否顺畅 |
| 第二批：岗位准备 | 图片 JD 提取、岗位字段核对、准备中询问、匹配分析、补充问题和学习清单；修复重复检索 | 截图信息是否完整，未知是否正确标记，状态切换是否按选择执行 |
| 第三批：定制简历 | 岗位项目推荐、用户调整、LLM 全文撰写、编辑确认、版本保存、Word/PDF 导出 | 两种不同 JD 的选项和内容是否合理，事实是否准确，导出是否可直接使用 |
| 第四批：联调验收 | 真实模型闭环、离线故障回归、迁移/恢复、连续操作、用量与耗时报告 | 正常完成完整流程；失败信息可理解；工程测试与模型效果分别报告 |

每批完成后先让用户体验，再继续后续批次。本轮已获授权，按已确认范围实施。

## 7. 验收原则

工程验收检查数据与状态一致、重复操作、无刷新更新、预算、错误恢复及导出质量。

模型效果验收以用户原简历、其他项目材料和真实 JD 为依据。至少比较两个要求明显不同的岗位，人工检查分类、漏项、项目归属、匹配理由、关键事实和生成内容。开发样例与最终检查样例分开，修过的失败样例作为回归，不能再宣称未见过的独立评测。

LLM 的结构正确不等于语义正确；离线模拟测试通过不替代真实模型的完整任务。发现错误要保留原结果、原因及修复后的对照。
