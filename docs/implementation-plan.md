# 分阶段实施计划

日期：2026-09-13。依据[需求与验收标准](requirements.md)。本文保留原分阶段计划；阶段一的本地基础、模拟测试和非敏感文本真实 API 连通性已完成，执行证据见[阶段一记录](stage-one-report.md)。阶段二已完成，见[阶段二记录](stage-two-report.md)；阶段三最小闭环已完成，见[阶段三记录](stage-three-report.md)；阶段四、五仍为计划。

## 推进方式

每阶段采用同一节奏：先用中文解释问题和设计 → 实现最小可运行切片 → 用适当测试验证 → 展示结果和限制 → 更新完成状态。正常、可逆的实现与测试无需逐项审批；遇到新增付费服务、扩大数据上传或核心范围变化时再询问。

从第一次保存事实开始就做来源、确认状态、防重复与隐私保护；阶段四负责补齐故障与恢复覆盖，不能把这些约束全部延后。模拟模型必须走实际 LangGraph 分支，不能用另一个假流程代替待测图。

## 阶段二：数据与基础界面

**目标：** 先证明数据能正确导入、确认、查询、修正与留存，建立后续生成可信材料的事实基础。

**设计与实现：**

1. 建立带 schema 版本的业务库，定义来源、事实确认/修订、岗位、任务、材料、进展等必要实体；按当前切片逐步增表。
2. 建立原始文件保存与本地 PDF/TXT/Markdown 提取。先用程序提供确定的原文和来源定位，再将模型提取结果作为可修改的候选字段；未配置 API 时使用手工录入或明确标记的模拟数据。
3. 实现原文/来源与候选事实并排核对、明确确认按钮、偏好设置；首次事实写入就验证来源与确认状态。
4. 实现粘贴 JD、原文保存、结构化字段校对，以及结合公司/ID/批次/正文的重复提示。
5. 实现岗位看板、手工状态变化历史、备注和待办。材料版本关联入口可随阶段三接入真实版本，不伪造已有材料。

**模型与程序：** 模型只建议提取字段；程序决定是否入库为已确认事实、保留哪些修订，以及是否允许状态更新。模型不得从文件缺失信息推断负面能力结论。

**关键代码（待创建）：** `services/documents.py`、`services/profile.py`、`services/jobs.py`、`db.py`、`schemas.py` 和对应模板；导入请求经过参数校验后调用 service，再显示待确认结果。

**验证：** 文字型 PDF、空/损坏/扫描型 PDF、非 UTF-8 与不支持格式；路径越界与同名上传；事实修改与重复确认；JD 原文不变、未写字段为空、同名不同批次不合并；状态历史与事务一致性。用文件哈希检查原始材料未被修改。

**对应验收：** A01–A04、A08、A10、A12、A14 的基础行为；真实样本相关部分仍需实际资料核验。

**学习重点与限制：** 讲清“解析出来的文本”“模型建议字段”“用户已确认事实”的区别。此时可以管理资料和岗位，但未完成 Agent 分析与材料闭环。

## 阶段三：Agent 最小闭环

**目标：** 实际运行一个能检索、判断缺口、等待用户、生成材料并确认保存的单主 Agent。

**设计与实现：**

1. 建立结构化查询和中英关键词检索基线，所有证据返回可回查的来源 ID；草稿不进入经历证据索引。
2. 实现工具白名单、参数与结果长度校验、预算扣减。真实运行需看到模型提出工具调用、程序执行、模型接收结果的完整轨迹。
3. 用 LangGraph 串联检索与三类结论分析，检查每条结论的 JD 要求和证据/缺口。
4. 缺信息时持久化中断；支持回答、稍后回答、暂不回答。新增事实展示后由用户确认，跳过保持未知。
5. 从已确认事实生成简历段落/项目介绍/自我介绍建议与修改依据；待核实项单列。
6. 持久化等待编辑确认；用事务与唯一操作 ID 保存版本，可导出 Markdown/TXT，原件与求职状态保持正确。

**设计原因与分工：** 模型选择检索方向并组织语言；程序限制它只能看允许的资料，验证引用和状态，用户决定事实与最终材料是否确认。中断使用本地持久化检查点，第一次闭环就覆盖重启后等待状态恢复。

**关键代码（待创建）：** `agent/graph.py` → `agent/model.py` ↔ `agent/tools.py` → `services/tasks.py` / `services/drafts.py`；页面通过任务 ID 提交补充与确认，再调用恢复入口。

**验证：** 使用模拟模型跑实际图的有证据、明确不符、资料不足三类分支；检索不到结果、学习资料冒充经历、引用不存在、未确认事实、无据数字；暂不回答不反复追问；等待补充/确认时关服务重启；重复确认只生成一个材料版本。至少一个模拟场景必须真实调用检索函数，不能只返回预写文本。

**对应验收：** A03、A05–A10、A12、A13 的闭环基线。真实 DeepSeek 工具调用和草稿真实性另外用用户确认资料验证。

**学习重点与限制：** 演示普通函数与模型工具调用区别、图状态和业务表区别、证据怎样进入生成。引用存在不能自动证明语义正确，草稿仍需人核对。

## 阶段四：可靠性

**目标：** 在重启、重复请求、外部故障和恶意资料条件下，已有闭环仍可解释、可恢复且预算有限。

**设计与实现：**

- 补齐异常发生在请求前后、业务提交前后、检查点写入前后的恢复处理；检查点与业务写入不同步时靠已提交操作 ID 对账。
- 补齐并发重复请求、旧页面重复确认、版本冲突、原件和事实隔离；任务串行领取不能只靠前端禁用按钮。
- 统一超时/限流/鉴权/余额/参数/非法输出的错误分类；有限重试计入持久化预算，恢复不清零。
- 记录每次请求和工具尝试、耗时、返回 Token、未知用量及可选金额估算；超预算停止并显示已有进度。
- 完成路径与工具参数限制、JD 注入测试、界面转义和请求来源校验、假密钥脱敏与 Git 忽略检查。

**模型与程序：** 模型输出不能决定是否越过预算、调用工具或写库；恢复规则和错误处理由程序保证。模型的语义错误通过真实核验发现，不能靠再加一个审核 Agent 宣称解决。

**关键代码（待创建/完善）：** 配置与模型适配器的预算/异常处理、`services/tasks.py` 的领取与恢复、`db.py` 的事务/唯一约束、图的保存与中断节点、安全边界测试。

**验证：** 模拟超时、429、401、400/422、402、500/503、截断或非法 JSON、未知工具与大量工具请求；每例断言最大调用次数和安全错误。使用独立进程退出/重启验证 A09；在业务已提交但检查点未更新处注入失败，验证 A10。用假 Key 检查响应、模板、日志、检查点，不能用真 Key 做快照测试。

**对应验收：** 重点补齐 A07–A14，同时重跑受变更影响的基础测试。

**学习重点与限制：** 解释“重试”为什么会多花费用、“幂等”如何防业务重复、为何本地无法确保已发出的远程请求只计费一次。单机单用户是明确边界，不承诺服务高可用。

## 阶段五：验收与展示

**目标：** 用可追溯证据证明首版能帮助真实求职，并产出用户能够讲解的项目材料。

**设计与实现：**

1. 从一份用户确认资料和一条真实 JD 开始，逐步收集约 10 条 JD；在提示词调试前划分开发样本与留出样本，例如 7＋3，具体随有效样本量记录。
2. 固定该次代码、提示词、模型配置与资料版本；逐个运行原文导入、分析、追问、草稿、确认保存与手动状态更新。
3. 原始材料和人工核验形成参考记录，逐条判断是否有依据。记录错误类型、样本数/结论数、人工或提示词修改次数、模型与工具请求数、Token、耗时和估算成本。
4. 留出集用于最终检查，不能一边拿留出样本修改提示词一边声称独立验收；若据此修复，记录污染并重新准备未使用样本或如实标明限制。
5. 在干净虚拟环境验证文档中的安装、配置、启动与默认离线测试，记录平台和依赖组合。
6. 交付中文版架构讲解、启动/使用说明、无隐私的虚构演示资料、演示步骤、评测记录、失败案例和后续计划。

**模型与程序：** 模型生成待核对结果，程序记录原始版本和运行指标；最终参考判断由人工对照原文，模型不能自行签发“验收通过”。

**关键文件（待创建）：** `scripts/evaluate.py`、公开虚构样例、`docs/evaluation-report.md`、运行说明与演示文档；真实输入及逐条私有结果存 `data/` 或被忽略的私有目录。

**验证与完成条件：** 对 A01–A15 逐项填“通过/失败/未测”及证据路径；真实接口未验证的项不得用模拟结果替代。A06 只报告已人工检查样本中的无据新增情况，不承诺所有未来输入绝无幻觉。遇到失败先记录，再修复并重测相关场景。

**学习重点与限制：** 用户能从输入讲到保存、解释工具校验和恢复、复现测试，并说明样本规模、成本、语义错误和首版边界；不编造秋招效果或录用概率。
