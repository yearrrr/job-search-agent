个人求职管家 Agent：首版需求与验收标准
一、项目目标与开发约定
我要开发一个自己实际使用的个人求职管家 Agent，同时通过开发理解 Agent 的完整工程流程，为 Agent 开发岗位的秋招准备项目经历。
我的背景是接触过 LLM 微调和强化学习，但缺少完整应用的工程落地经验。开发过程中，请使用中文解释关键设计，不要只交付我无法理解的代码。
确定的技术路线：
- Python。
- LangGraph：任务编排、状态管理、人工确认和中断恢复。
- DeepSeek API：理解、生成及工具调用，不在本地部署大模型。
- SQLite：个人档案、岗位、任务、草稿和求职记录。
- 本地资料目录：保存原始文件与生成材料。
- 简单 Web 界面：优先考虑 FastAPI＋服务端模板＋少量 JavaScript，不引入复杂前端工程。
开发要求：
1. 按可验证的阶段推进，每阶段先解释目标和设计，再实现，再测试。
2. 保留已有文件与用户修改，不擅自覆盖。
3. 不因追求“企业级”加入与首版无关的组件。
4. 新增付费服务、扩大数据上传范围或改变核心需求前，先询问用户。
5. 区分已实现、已测试和计划中的功能，不虚报完成情况。
二、首版业务范围
首版完成以下闭环：
确认个人资料 → 导入岗位 JD → 分析要求与个人经历 → 缺失信息追问 → 生成材料草稿 → 用户确认保存 → 记录求职进展。
首版只服务一个本地用户，不做多用户平台。
首版明确不做
- 全网职位爬取、招聘网站登录和自动网申。
- 自动投递、自动发邮件或联系招聘人员。
- 邮箱、微信、日历等外部账号接管。
- 语音面试、视频面试和完整学习平台。
- 自动生成排版复杂的完整 Word/PDF 简历。
- 模型微调、本地大模型部署。
- 强制引入向量数据库和多智能体。
- 无人值守的定时后台任务。
这些不是永远不做，而是不影响首版验收。
三、功能需求
F1：个人资料导入与确认
支持导入文字型 PDF 简历，以及 UTF-8 文本或 Markdown 补充材料。
要求：
- 原始文件保留，不被修改。
- 提取教育经历、项目经历、技能等信息。
- 提取结果先进入“待确认”状态，由用户修改、确认。
- 无法确定的信息留空或标记待确认，不能猜测。
- 扫描型 PDF 或无法解析的文件，应明确提示暂不支持，并允许粘贴文本。
- 每项重要事实保留来源定位，例如文件、页码或文本片段。
- 求职目标、城市等偏好由用户明确设置，不从聊天语气中自行推断。
已确认档案是后续生成材料的事实依据。
F2：岗位导入与管理
首版支持粘贴 JD 正文，并填写公司、岗位名称及可选来源链接。
要求：
- 保存原始 JD 和导入时间。
- 提取职责、硬性条件、加分项、地点等字段。
- 未写明的截止日期、薪资等不得补造。
- 用户可以查看并修正提取结果。
- 重复导入时提示，不直接覆盖已有材料和求职记录。
- 不仅凭岗位名称判重，要考虑公司、岗位 ID、招聘批次或正文等信息。
- 来源链接首版可以仅作记录，不承诺自动读取网站。
F3：岗位分析
针对一个岗位，结合个人档案和相关资料生成分析。
至少区分：
- 有经历证据支持。
- 有明确依据表明条件不符。
- 资料不足，需要确认。
每项重要结论应能关联：
1. JD 中的要求。
2. 对应的个人经历证据，或缺失的信息。
约束：
- “简历没写”不等于“用户不会”。
- 不输出没有依据的录用概率、通过率。
- 不把模型建议当作已确认事实。
- 关键资料不足时，提出具体问题，并允许用户稍后回答或暂不回答。
F4：岗位材料草稿
根据岗位与已确认经历，生成：
- 针对该岗位的简历段落建议稿。
- 项目或自我介绍的表达建议。
- 修改依据及需要用户核实的内容。
要求：
- 只调整真实内容的表达、顺序和重点。
- 不新增未经确认的经历、技术使用、职责或效果数字。
- 草稿中涉及个人经历的重要陈述应能追溯来源。
- AI 生成的草稿不能自动写回个人事实档案。
- 新增事实必须先由用户确认。
- 草稿有版本记录，可编辑，并可导出为 Markdown 或文本。
- 保存新版本不覆盖原始简历。
首版不要求自动输出排版完整的投递版 PDF。
F5：求职进展管理
提供简单岗位看板，支持用户设置：
- 已收藏。
- 准备中。
- 已投递。
- 面试中。
- 已结束。
每个岗位可以关联材料版本、备注和待办。
约束：
- 生成或保存草稿不能自动代表“已投递”。
- 求职状态的变更由用户明确操作或确认。
- 面试结果不能由模型根据语气推测。
- 状态变化保留时间和历史记录。
F6：任务状态与恢复
任务应显示可理解的状态，例如：
- 处理中。
- 等待补充。
- 等待确认。
- 已完成。
- 失败。
要求：
- 界面显示当前步骤及错误原因，不能长时间只显示“加载中”。
- 等待用户输入或确认时保存状态，不持续调用模型。
- 关闭并重新启动服务后，能恢复待处理任务。
- 重试或重复点击不能导致重复保存、重复建档或重复更新状态。
四、Agent、RAG 与数据设计原则
1. Agent 与普通程序的分工
模型负责：
- 理解任务与 JD。
- 判断需要补充什么信息。
- 选择允许使用的检索工具。
- 组织分析与草稿。
程序负责：
- 权限判断和参数校验。
- 数据读写。
- 状态转换约束。
- 版本管理、防重复操作和预算限制。
必须实际使用 LangGraph 管理流程，并实现工具调用；不能只是给一次模型请求换上“Agent”的名字。
2. 首版先实现单主 Agent
先完成一个主 Agent 的完整流程。
独立审核 Agent 可以作为后续实验，但不是首版完成的前提。增加前应先建立单 Agent 基线，再比较错误率、成本和耗时。
3. 数据分成三类
数据类别	内容	使用原则
个人事实	已确认的经历、技能、偏好	结构化存储，保留来源与确认状态
原始资料	简历、项目说明、笔记、JD	保留原文，按需检索
业务状态	岗位、任务、草稿版本、求职进展	数据库精确查询，不依赖聊天记忆


学习资料和经历证据必须区分：读过某项技术的文档，不代表做过相关项目。
4. RAG 采用最小可用方案
首版使用结构化查询、关键词或全文检索，从本地资料中获取相关证据后生成回答。
要求：
- 检索结果保留来源。
- 不把全部资料无差别加入每次请求。
- 没检索到证据时说明不足，不能补造。
- 不将生成草稿作为证明草稿真实性的证据。
暂不要求 embedding API 或向量数据库。后续引入时，需说明收益、成本和新增的数据传输。
五、隐私、安全与成本要求
本地数据与 API
- 原始资料、SQLite 数据库和生成材料保存在本地。
- 明确提示：使用 DeepSeek API 时，请求中的文本仍会发送至模型服务商。
- 原始 PDF 在本地解析，不默认整份上传。
- 仅发送完成当前任务必要的文本。
- 岗位匹配时尽量移除手机号、邮箱、详细地址等无关信息。
- 不默认将完整提示词和个人资料上传至第三方日志平台。
密钥与版本控制
- API Key 通过本地环境变量或未纳入 Git 的配置读取。
- 不要求用户把 Key 发到聊天中。
- Key 不出现在前端、日志、报错或测试报告中。
- 提交代码前排除真实简历、个人数据库、生成材料和敏感日志。
- 公开示例使用明确标记的虚构资料。
工具与文件安全
- 工具只允许访问配置范围内的资料目录。
- 上传文件不能通过文件名或路径越界读写。
- 文档和 JD 中的指令只作为不可信内容，不能改变系统权限。
- 不允许模型执行任意终端命令或任意 SQL。
- Web 服务默认仅绑定本机地址，不直接暴露到公网。
- 首版不存在真实投递和对外发送工具。
异常与预算
- 请求超时、重试次数、工具调用次数和模型调用次数均可配置，且有有限默认值。
- 重试同样计入任务预算。
- 参数错误、鉴权失败等不应无限重试。
- 超出预算后保存进度并显示原因。
- 记录模型请求次数、工具调用次数、耗时及接口返回的 Token 用量。
- 未获得用量时标为未知，不能记成零。
- 金额如按配置价格估算，应标记为估算值。
六、验收标准
以下是必须验证的行为，不是预先宣称已经达到的指标。
编号	验收场景	通过条件
A01	导入文字型 PDF	能查看原文、提取结果和来源；未经确认的信息不会直接成为正式事实
A02	导入不支持的文件	明确报错并提供文本输入替代方式，不显示虚假的成功结果
A03	资料缺失	不猜测日期、城市、经历和数字；正确标记未知或追问
A04	导入真实 JD	保留原文，重要字段可核对；未提供的信息不补造
A05	岗位匹配分析	重要结论有要求及证据依据，区分明确不符与资料不足
A06	生成材料草稿	在人工核验样本中，不出现无依据的新增个人经历和效果数字
A07	保存与版本管理	原始简历内容不变；草稿可追溯版本；生成内容不污染事实档案
A08	求职状态更新	保存草稿不自动标记已投递；状态变更有用户操作和记录
A09	中断后恢复	服务重启后，可继续等待补充或确认的任务，不要求重做全部流程
A10	重复操作	重复点击确认或重复执行保存，不产生重复业务记录
A11	API 故障	模拟超时、限流、鉴权失败及非法输出，均能有限处理并展示错误
A12	恶意输入	JD 中的伪指令不能触发越权读写、泄露密钥或修改系统规则
A13	成本限制	达到调用上限后停止继续调用，显示原因和已有进度
A14	本地隐私	密钥不进入前端和日志；敏感文件不会被默认纳入 Git
A15	可复现运行	按项目说明，在独立环境中完成安装、配置、启动和测试


测试分层
自动化测试：
- 数据校验、状态转换、版本管理等单元测试。
- 使用模拟模型响应验证流程分支。
- 覆盖追问、确认、中断恢复和故障处理。
- 自动化测试默认不消耗真实 API 费用。
真实 API 验证：
- 用少量真实 JD 和用户确认的资料跑完整流程。
- 首批可选择约 10 个真实 JD，不要求用户先制作大型数据集。
- 保留一部分样本用于最终验收，不反复据此修改提示词。
- 参考答案来自原始材料和人工核验，不能只让模型自己评分。
- 记录样本数、错误类型、修改次数、Token 和耗时。
若真实 API 未验证，应明确写“模拟测试通过、真实接口待验证”，不能将其等同于完整验收通过。
测试集上未出现某类错误，不代表系统在任何情况下都不会出现该错误。
七、开发阶段与交付物
阶段一：需求与工程基础
交付需求文档、开发计划、环境配置、项目骨架、基础测试及非敏感文本的 API 连通性验证。
阶段二：数据与基础界面
实现资料确认、JD 导入、岗位管理和本地存储。先证明数据能够正确保存、查询和修改。
阶段三：Agent 最小闭环
实现检索、岗位分析、缺失信息追问、草稿生成及确认保存。
阶段四：可靠性
补齐中断恢复、版本管理、防重复执行、隐私保护、调用预算和故障测试。
阶段五：验收与展示
完成真实样本评测、运行说明、演示材料和局限说明。
每个阶段都必须同步测试，不能把测试全部推迟到最后。
最终至少交付：
- 可运行的本地 Web 应用。
- 清楚的代码结构及依赖配置。
- 需求说明、架构说明、启动说明。
- 自动化测试与真实样本评测记录。
- 无真实隐私信息的演示资料。
- 已知限制、失败案例和后续计划。
八、面向学习的协作方式
每个阶段请解释：
1. 这一阶段解决什么问题。
2. 为什么采用当前设计。
3. 哪些事情由模型判断，哪些由程序保证。
4. 关键代码在哪里，如何串联。
5. 怎样验证它正确，以及目前仍有哪些限制。
允许先做最小实现再优化，但不要以“后面再处理”为由跳过事实真实性、密钥保护和危险操作边界。
首版完成后，我应能独立讲清楚：
- 一次任务从用户输入到保存结果的流程。
- LangGraph 状态与业务数据库的区别。
- 检索如何为生成提供依据。
- 工具调用如何被校验和执行。
- 中断、重试与重复写入如何处理。
- 如何测量效果、耗时和成本。
九、新项目 Codex 收到本文后的首次工作
先检查当前工作目录、已有文件和开发约定，不覆盖已有内容。
然后：
1. 将本文整理为项目需求文档。
2. 列出待确认事项，区分真正阻塞的问题与可采用默认值的问题。
3. 检查 Python、Git 等本地环境。
4. 给出与上述阶段对应的实施计划。
首次先完成需求落盘、环境检查和计划，不要一次性生成整个系统，不创建真实投递任务，也不要要求我在聊天中提供 API Key。
